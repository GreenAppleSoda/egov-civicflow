# 민원 접수·처리 시스템 요구사항 정의서

| 항목 | 내용 |
|---|---|
| 프로젝트 | eGov-CivicFlow (민원 접수·처리 시스템) |
| 문서 버전 | v0.3 |
| 작성일 | 2026-11-18 |
| 기술 기반 | 전자정부 표준프레임워크 5.0 (Boot), MyBatis, MariaDB |

## 1. 개요

### 1.1 목적

민원인이 민원을 접수하고, 담당자가 처리·답변하며, 관리자가 배정·통계를 관리하는 민원 처리 시스템을 전자정부 표준프레임워크 기반으로 구현한다.

### 1.2 범위 원칙

처음부터 모든 기능을 만들지 않고 **핵심 흐름(등록 → 접수 → 배정 → 처리 → 답변 → 완료)을 끝까지** 구현하는 것을 1차 목표로 한다.

- 우선순위 **P1**: 1차 구현 대상
- 우선순위 **P2**: 핵심 흐름 완성 후 추가할 기능

### 1.3 요구사항 ID 규칙

요구사항은 `접두어-구분-번호` 형식의 ID로 관리하며, 이후 산출물(테이블 정의서, 화면 설계서, 테스트)과 커밋 메시지에서 이 ID로 추적한다.

```
FR - C - 01
│    │    └─ 일련번호 (같은 묶음 안의 순서)
│    └────── 역할 구분 (기능 요구사항에만 사용)
└─────────── 요구사항 종류
```

| 접두어 | 의미 | 형식 | 예시 |
|---|---|---|---|
| FR | Functional Requirement (기능 요구사항) | FR-역할-번호 | FR-C-01 |
| BR | Business Rule (업무 규칙) | BR-번호 | BR-05 |
| SR | Security Requirement (보안 요구사항) | SR-번호 | SR-01 |
| BT | Batch (배치 요구사항) | BT-번호 | BT-01 |

| 역할 구분 | 의미 | 역할 코드 |
|---|---|---|
| C | Citizen (민원인) | CITIZEN |
| O | Officer (담당자) | OFFICER |
| A | Admin (관리자) | ADMIN |

- 한 번 부여한 ID는 재사용하지 않는다. 요구사항을 삭제해도 번호는 비워 둔다.
- 커밋 메시지에는 `feat: 민원 등록 구현 (FR-C-02)`처럼 ID를 함께 적는다.

## 2. 사용자 역할

| 역할 | 코드 | 설명 |
|---|---|---|
| 민원인 | CITIZEN | 회원가입 후 민원을 등록하고 처리 결과를 확인하는 일반 사용자 |
| 담당자 | OFFICER | 자신에게 배정된 민원을 처리하고 답변하는 공무원 역할 |
| 관리자 | ADMIN | 계정, 분류, 배정, 통계, 공지를 관리하는 역할 |

## 4. 민원 상태

상태는 영문 코드로 저장하고 화면에는 한글로 표시한다.

| 코드 | 한글 | 종결 여부 |
|---|---|---|
| RECEIVED | 접수 | 진행 |
| ASSIGNED | 배정 | 진행 |
| IN_PROGRESS | 처리중 | 진행 |
| COMPLETED | 완료 | 종결 |
| REJECTED | 반려 | 종결 |
| CANCELED | 취소 | 종결 |

### 4.1 상태 전이

| 현재 상태 | 다음 상태 | 수행 주체 | 조건 |
|---|---|---|---|
| 접수 | 배정 | 관리자 | 담당자 지정 |
| 접수 | 취소 | 민원인 | 본인 민원 |
| 접수 | 반려 | 관리자 | 사유 필수 |
| 배정 | 처리중 | 담당자 | 배정된 담당자 |
| 배정 | 반려 | 담당자 | 사유 필수 |
| 처리중 | 완료 | 담당자 | 답변 필수 |
| 처리중 | 반려 | 담당자 | 사유 필수 |
| 완료, 반려, 취소 | 없음 | | 종결 상태 |

담당자 재배정은 상태가 바뀌는 것이 아니라 담당자만 바뀌는 것이므로 위 전이표에 넣지 않고 업무 규칙 BR-09로 정의한다.

## 5. 업무 규칙

| ID | 규칙 |
|---|---|
| BR-01 | 상태가 바뀔 때마다 이력을 남긴다. (누가, 언제, 이전 상태 → 이후 상태, 메모·사유) |
| BR-02 | 조회 권한은 민원인은 본인 민원, 담당자는 배정된 민원, 관리자는 전체이다. |
| BR-03 | 반려는 사유가 필수이고, 완료는 답변이 필수이다. |
| BR-04 | 종결 상태(완료, 반려, 취소)의 민원은 수정할 수 없다. |
| BR-05 | 민원인의 수정·취소는 접수 상태에서만 가능하다. |
| BR-06 | 처리 기한은 접수일로부터 7일이며, 초과 민원은 배치가 표시한다. |
| BR-07 | 첨부파일은 최대 3개, 개당 5MB 이하, 허용된 확장자만 받는다. |
| BR-08 | 첨부파일은 무작위 이름(UUID)으로 저장하고 원본 파일명은 DB에 별도로 보관한다. |
| BR-09 | 담당자 재배정은 관리자가 배정(ASSIGNED) 상태에서만 할 수 있다. 상태는 그대로 유지하고 담당자만 바꾸며, 이력에는 이전·이후 상태를 모두 ASSIGNED로 하고 새 담당자와 사유를 함께 기록한다. 새 담당자는 활성 상태의 담당자 역할이어야 하고 현재 담당자와 달라야 한다. 처리중 이후에는 담당자를 바꿀 수 없다. |

## 6. 보안 요구사항

| ID | 요구사항 |
|---|---|
| SR-01 | 비밀번호는 해시하여 저장한다. |
| SR-02 | 역할별 접근 제어를 서버에서 검증한다. (화면 숨김만으로 처리하지 않는다.) |
| SR-03 | 첨부파일은 확장자, 크기, 경로 조작 여부를 검증한다. |
| SR-04 | SQL Injection, XSS, CSRF에 대한 방어를 적용한다. |
| SR-05 | 애플리케이션은 프로젝트 전용 DB 계정(최소 권한)으로 접속하고, 접속 정보는 저장소에 올리지 않는다. |

## 7. 배치 요구사항

핵심 흐름 구현 후 추가한다.

| ID | 배치 | 설명 |
|---|---|---|
| BT-01 | 일별 통계 집계 | 일별 민원 접수·처리 건수를 집계하여 저장 |
| BT-02 | 기한 초과 표시 | 처리 기한을 넘긴 민원을 표시 |
| BT-03 | 첨부파일 정리 | 임시·고아 첨부파일 삭제 |

## 8. 설계 기본 결정 사항

1. 담당자 배정은 관리자가 수동으로 한다. (자동 배정은 1차 범위 제외)
2. 한 사용자는 하나의 역할만 갖는다. (`users` 테이블의 역할 컬럼 하나)
3. 회원만 민원을 등록할 수 있고 비회원 접수는 없다.
4. 회원가입은 민원인만 가능하다. 담당자·관리자 계정은 관리자가 생성하고, 최초 관리자는 시드 데이터로 넣는다.
5. 첨부파일은 서버 디스크 경로에 저장하고, DB에는 경로와 메타정보만 둔다.

## 9. 1차 범위 제외

- 분류별 자동 배정
- 다중 역할, 비회원 접수
- 처리중 상태에서의 담당자 재배정·이관 (FR-O-05)
- 공공데이터 연계 (FR-A-07)
- 내 정보 변경 (FR-C-07)
